# 模板示例图与配方扩展简报

状态：阶段 A 已完成；阶段 B 与 12 个新配方仍等待单独批准

准备时间：2026-08-15

## 当前体验

- Vistack 目前有 30 个内置模板，其中只有 `桌面手办风格` 绑定了示例图，其余 29 个显示分类文字占位块。
- 模板卡片为纵向列表，图片区域目前只有 64×64 像素；即使补图，方形裁切也不利于展示人像、海报和产品主视觉。
- `public/1.png` 正在被手办模板使用，`public/2.png` 当前没有模板引用。本阶段不删除或覆盖这两个旧文件。
- 上游 GPT-Image2-Skill 提供大量分类和示例，但整库导入会带来包体、来源维护和风格不统一问题。

## 已确认的本地生图能力

本机已安装 `codex-image` CLI，并检测到 `OPENAI_API_KEY` 与 `OPENAI_BASE_URL` 已配置。CLI 支持：

- `generate`、`edit` 和 `generate-batch`；
- 模型、尺寸、质量、背景、格式、压缩率和生成数量；
- 批量并发、固定输出目录、失败控制和 `--dry-run`；
- 使用 OpenAI-compatible Images API 的 `/v1/images/generations` 与 `/v1/images/edits`。

无费用预检已通过：`gpt-image-2`、`4:5@1k`、`medium`、WebP 能正确解析为 `1024x1280` 的 Images API 请求和指定输出路径。该预检没有调用 API。

尚未确认的唯一关键点是实际端点认证和真实出图质量。确认它们需要至少一次会产生费用的真实生成，因此不能在未确认预算前自动执行。

## 推荐产品方案

### 1. 所有内置模板都有结果预览

- 新预览统一放在 `public/template-previews/`，文件名与模板 ID 对应。
- 使用 4:5、1024×1280、WebP、medium 质量，优先把单张文件控制在 350 KB 内。
- 示例图只展示预期结果，不伪装成质量承诺；不使用上游图库图片，不带品牌 logo、水印或真实人物身份。
- 人像、K-pop、产品、摄影和叙事模板各自展示真实主题，不用一套装饰风格覆盖所有类别。
- 精准改图配方使用统一的虚构人物/产品素材语境，让不同配方之间更容易比较，但卡片只展示最终效果。

### 2. 模板卡片做轻量视觉整理

- 保留现有模板面板、分类、搜索、语言切换和“插入主提示词”流程。
- 缩略图改为稳定的 4:5 竖图，建议 80×100 像素；标题、说明和标签继续放在右侧。
- 图片使用懒加载和异步解码；加载失败时仍显示当前文字占位，不让卡片塌陷。
- 不新增主导航、图库页面、营销式大卡或多层卡片，也不改变提示词写入行为。

```text
┌────────┬──────────────────────────────┐
│ 4:5 图 │ 模板标题        需参考图 双语 │
│        │ 一行到两行用途说明             │
│        │ 标签                         │
│        │ [插入主提示词]                │
└────────┴──────────────────────────────┘
```

### 3. 新增 12 个高频精准改图配方

与现有 6 条合并后，`精准改图配方` 共 18 条。建议新增：

1. 只换发型。
2. 只改妆容。
3. 只改表情。
4. 只改姿势。
5. 添加或移除指定配饰。
6. 移除指定物体并自然补全背景。
7. 改变产品颜色或材质。
8. 改变时间、天气或光线，保持构图与主体。
9. 扩图并改变画布比例。
10. 保持身份进行视觉风格转换。
11. 老照片修复、去损伤与清晰化。
12. 把产品自然植入目标使用场景。

这些配方继续使用明确的参考职责、需要改变、必须保持和错误限制，不复制上游带作者来源的社区 Prompt。

## 生产流程

### 阶段 A：4 张试产

先生成四个差异明显的示例：自然手机自拍、K-pop 概念照、产品静物、精准文字/改图配方。每个任务只生成 1 张，使用 medium 质量和 4:5 WebP。

试产只回答四个问题：

- 端点和 `gpt-image-2` 是否真实可用；
- 4:5 缩略图在模板列表中是否清楚；
- WebP 体积是否适合进入仓库；
- 不同类别的视觉质量是否足够稳定。

#### 阶段 A 结果（2026-08-15）

- 用户批准后执行了恰好 4 次付费 `gpt-image-2` 请求；全部首次成功，没有重试，也没有发送第 5 次请求。
- 四个任务统一使用 `4:5@1k`、`medium`、WebP、压缩率 82、单张输出，实际文件均为 1024×1280。
- 结果文件为 `phone-selfie-natural.webp`（98,520 字节）、`kpop-studio-concept.webp`（68,922 字节）、`luxury-product-still.webp`（62,876 字节）和 `gpt-image2-edit-exact-text.webp`（119,628 字节），均低于 350 KB 上限。
- 自然自拍、K-pop 棚拍和产品静物在缩略图中主题清楚；文字海报准确显示“夏夜影像计划”和“2026.08.15 / 19:30”。海报城市背景中仍有极小的不可读招牌细节，但不值得在未批准的情况下追加付费重试。
- 四张图已经绑定到对应模板。模板缩略图改为稳定的 80×100 4:5 比例，并启用懒加载和异步解码；搜索、分类、语言切换和提示词插入行为保持不变。
- 桌面端逐张搜索和 390×844 手机尺寸检查通过，没有水平溢出；四个图片资源均加载为 1024×1280，页面没有应用自身的控制台错误。
- 可复现请求清单保存在 `scripts/template-preview-pilot.jsonl`，其中不包含 API Key。

### 阶段 B：完整批量

试产通过后，再生成 30 个现有模板与 12 个新增配方的完整预览，共 42 张。批量并发限制为 2，保留可复现的 JSONL 清单和生成参数，但绝不记录 API Key 或完整敏感连接信息。

## 保持不变

- 不修改 Vistack 的生图 API payload、供应商路由、模型参数或连接预设。
- 不修改历史、资产库、IndexedDB、用户模板、Prompt Pool 或已有图片。
- 不删除 `public/1.png`、`public/2.png` 或用户自有 `排查/` 目录。
- 不把外部 Python CLI、上游 400 MB 级图库或外部作者图片打包进产品。

## 风险与费用边界

- 真实试产和完整批量都会调用当前配置的外部生图端点并产生费用，具体单价由该端点决定，CLI 无法在请求前可靠给出金额。
- 42 张一次性生成的浪费风险较高，因此必须先完成 4 张试产并由用户确认视觉方向。
- 预览图只能帮助选择模板，不能证明图生图身份保持、局部编辑或准确文字在所有供应商上都同样有效。

## 验收条件

- 每个内置模板都有存在且可加载的 4:5 WebP 预览路径。
- 新增 12 个配方拥有中英文 Prompt、独立 ID、标签、说明和预览图。
- 模板搜索、分类、语言切换和写入主提示词行为保持不变。
- 桌面和 390×844 手机尺寸无水平溢出，卡片高度稳定，图片加载失败有兜底。
- 自动检查验证模板 ID、图片文件、尺寸、格式和文件大小；`npm run check` 全部通过。
- 所有真实生成请求都在用户确认费用范围后执行，并记录请求数量，不记录密钥。
