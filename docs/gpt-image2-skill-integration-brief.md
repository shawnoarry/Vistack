# GPT Image2 Skill 与 Vistack 融合评估

状态：G3-lite 已实现；G1 能力档案与 G2 原生遮罩暂缓

调研时间：2026-08-15

参考仓库：[wuyoscar/GPT-Image2-Skill](https://github.com/wuyoscar/GPT-Image2-Skill)

核对基线：`068dd9e24aadc8731e46f38548ca4dcd94515d35`（2026-08-10）

## 一句话结论

不建议把这个项目作为 Python 依赖或整套图库直接塞进 Vistack。推荐采用“薄融合”：把它当作上游知识和协议参考，在 Vistack 现有 Vue/TypeScript、多供应商路由、历史资产和提示词助手中原生实现少量高价值能力。

如果目标是补齐 GPT Image 2 原生 API 能力，推荐顺序：

1. 先补 GPT Image 2 的 provider/model capability profile 和标准 Images API 参数。
2. 再把现有遮罩工具升级为“支持时走原生 alpha mask，不支持时保留当前视觉参考兜底”。
3. 最后只提炼与真实工作流相关的 Prompt Craft 规则和少量模板，不导入整套图库图片。

如果目标只是吸收提示词图库和写作方法，G1 不是前置条件，可以直接做不改请求层的 G3 轻量版本。

## 外部项目实际包含什么

该仓库包含三类能力：

- Agent Skill：让 Codex、Claude Code 等智能体先查询分类提示词和写作规则，再调用图像生成命令。
- Python CLI：用 OpenAI Python SDK 调用 `images.generate` 或 `images.edit`，支持生成、多参考图、mask、质量、输出格式等参数。
- Prompt Gallery：31 个分类、162 条提示词，并附带示例图和来源标记。

本次本地核对结果：

- 仓库约 419.18 MB，其中 164 张示例图约 418.45 MB。
- 162 条图库记录中，104 条标记为 `Curated`，58 条带 `Author + Source` 外部来源标记。
- 仓库主体是 MIT License，但其文档也明确要求继续保留外部来源 Prompt 的作者和出处。

因此，整库打包会明显增大前端体积，也会引入持续的来源和授权维护工作。

## Vistack 已经具备的重叠能力

Vistack 并不是从零开始接 GPT Image 2：

- 已能根据模型和参考图自动选择 `/images/generations` 或 `/images/edits`。
- 已支持多张参考图，并在发送前做兼容性的图片压缩。
- 已有 GPT Image 尺寸换算和部分供应商专用尺寸规则。
- 已有任务、历史、实际参数、逐图修订提示词和脱敏诊断。
- 已有创作模板、Prompt Pool、短词组和独立提示词助手。
- 已有本地遮罩画布，但当前把黑白遮罩作为第二张参考图发送，并不是真正的原生 API `mask` 字段。

这意味着融合重点不是新增一套生成器，而是补齐现有边界。

## G1 到底是不是必须

G1 不是所有融合方向的必需项。它的必要性取决于要融合哪一部分：

| 目标 | 是否需要先做 G1 | 原因 |
| --- | --- | --- |
| 只安装 Skill 给开发者使用 | 不需要 | 与 Vistack 产品运行时彼此独立。 |
| 只提炼 Prompt Craft 和少量提示词配方 | 不需要 | 可以只复用现有模板和提示词助手，不改生成请求。 |
| 补齐标准 OpenAI 的质量、背景、格式、压缩等参数 | 建议先做 | 同一参数并非所有供应商和端点都支持，需要明确发送边界。 |
| 把当前视觉遮罩升级为原生 alpha mask | 需要 | 必须先知道当前模型与端点是否支持原生 mask，并保留其他供应商兜底。 |
| 继续增加更多模型专用参数 | 需要 | 否则条件判断会继续散落在界面和请求代码中，回归风险逐渐增大。 |

因此，G1 的直接收益主要是请求正确性、兼容性和后续扩展安全，不会单独让生成质量明显提升。若当前优先目标是尽快获得提示词知识价值，应先做一个不改 API payload 的 G3-lite；若目标是原生遮罩和完整参数，G1 才是合理的第一步。

## 推荐融合架构

```text
GPT-Image2-Skill（上游参考）
        |
        | 人工筛选协议规则、Prompt Craft、少量示例
        v
Vistack 原生 TypeScript 能力层
  - 模型能力 profile
  - 请求参数适配
  - 原生 mask / 兼容兜底
  - 来源可追踪的提示规则
        |
        v
现有创作台、提示词助手、历史、资产库和多供应商路由
```

外部 Python CLI 不进入浏览器运行时，也不替换 Vistack 的 API Key、代理、预设或历史系统。

## 阶段 G1：GPT Image 2 能力档案

这是最推荐的第一步，也和当前项目 TODO 中的 provider/model capability profiles 一致。

建议新增一个小型、可测试的能力档案，至少描述：

- 协议：`images-generations`、`images-edits` 或现有供应商专用协议。
- 是否支持参考图、原生 mask、质量、背景、输出格式、压缩和 moderation。
- 尺寸格式、批量上限和参考图上限。
- 哪些参数只适用于生成，哪些只适用于编辑。
- generic fallback：未知模型继续保持当前行为，不猜测、不自动切换协议。

第一版只覆盖 Vistack 实际使用的 GPT Image、Doraverse、Grsai 和现有 Gemini 路径，不设计通用 manifest DSL。

用户可见变化应保持很小：只有当前模型明确支持时，才显示相应参数；未选择 GPT Image 2 时，现有界面和请求完全不变。

### G1 的安全拆分

为避免能力档案一加入就改变已经可用的请求，G1 应拆成两个独立步骤：

- G1a 能力登记：新增只读的能力表和测试，不接管界面默认值，不修改请求 payload，不改任何存储。现有运行行为必须逐项保持一致。
- G1b 能力启用：以后单独确认哪些新参数要显示和发送。只有用户明确选择新参数时才加入请求；旧配置没有该字段时继续保持“省略参数”，不能自动改成显式 `auto`。

G1a 不应影响已经保存的以下配置：

- API Key、接口地址、模型 ID、代理开关和代理令牌。
- 主生成连接预设和提示词助手连接预设。
- 生成批量模式、自定义模板、词组、历史、图片和资产分类。
- 已有历史记录中的比例、分辨率、实际参数和诊断。

当前比例、分辨率、质量、`autoPrompt` 和 `translate` 主要是当前会话状态，并不属于 API 连接预设。这里仍有一个需要专门锁住的回归点：现有界面会根据模型支持列表自动校正比例和分辨率。G1a 不得把新能力档案接入这段自动校正逻辑，否则可能在用户切换模型时改变当前选择。

模型列表缓存只是可重新获取的模型元数据，但 G1a 也不应迁移、清空或重写其存储格式。第一版应在读取后做运行时只读叠加，并让旧缓存继续正常使用。

### G1 验收条件

- 当前 Images、Edit、Chat、Grsai 和供应商专用请求快照全部通过。
- 标准 OpenAI GPT Image 2 路径可以按能力档案发送已确认支持的参数。
- 不支持的参数不发送，未知端点继续走 generic fallback。
- 历史中的 `actualParams` 记录最终发送的非敏感参数。
- API Key、代理 token、预设、历史图片和 IndexedDB 结构不迁移。
- G1a 前后的现有请求快照完全相同，比例、分辨率和批量数不会因为能力表出现而自动改变。
- 旧连接预设和旧模型缓存不新增必填字段；缺少新字段时继续使用当前兼容行为。

## 阶段 G2：原生遮罩与兼容兜底

这是外部项目对 Vistack 最有实际价值的一块，但需要在 G1 能力识别之后做。

当前遮罩画布输出的是“黑底白色涂抹图”。这适合作为不支持原生 mask 的视觉参考，但不能直接作为 OpenAI 原生 mask：原生 mask 依赖 alpha 通道，透明区域表示需要编辑，非透明区域表示保留。

推荐同时保留两种产物：

- 视觉遮罩：继续供 Gemini、Grsai 或未知模型作为第二张参考图使用。
- Alpha 遮罩：只在能力档案明确支持原生 mask 时，通过 multipart 的独立 `mask` 字段发送。

这样既能让 GPT Image 2 获得更准确的局部编辑，也不会破坏其他供应商当前可用的兜底行为。

### G2 验收条件

- 支持原生 mask 的端点收到 `image + mask + prompt`，遮罩不再混入普通参考图数组。
- 不支持或未知的端点继续收到当前“底图 + 视觉遮罩 + 提示词约束”。
- 原生遮罩尺寸必须与底图一致，PNG alpha 语义经过自动测试。
- 连续遮罩编辑、历史保存和工具箱送回创作台行为不变。

## 阶段 G3：Prompt 知识轻量融合

不建议新增一个装满 162 张大图的主导航图库。Vistack 已经有模板和 Prompt Pool，而且项目记录显示这些能力目前使用频率较低。

推荐只吸收两类内容：

1. Prompt Craft 规则，例如“场景到主体到细节到约束”“编辑时明确保持不变量”“多参考图按编号说明角色”“需要准确文字时明确列出原文”。
2. 与真实使用高度相关的少量配方，例如自拍、人物一致性、K-pop 路透、产品图、海报文字和局部编辑。

建议实现为 12 到 20 条结构化配方，不附带大图，接入现有模板面板和提示词助手。提示词助手根据任务类型只注入 1 到 3 条相关规则，避免把整套图库发送给模型。

如果直接改写或复制上游内容，应在 `THIRD_PARTY_NOTICES.md` 中记录仓库、固定 commit 和 MIT 来源；带外部作者来源的条目必须保留作者与链接。更稳妥的做法是优先使用 `Curated` 条目作为研究素材，再根据 Vistack 的真实场景重新编写。

### G3 验收条件

- 不增加新的主导航或常驻面板，只复用当前模板/助手入口。
- 首次包体不包含外部图库的 418 MB 示例图。
- 每条外部来源配方都有可追踪的 `source` 和 `attribution`。
- 选择配方只改写当前提示词，不改变模型、API 预设、参考图或历史。

### G3-lite 实施结果

用户于 2026-08-15 明确选择先实施最小版本。当前只在现有模板面板新增 `精准改图配方` 分类和六条双语配方：保持身份换场景、只换服装、只换背景、多参考图按角色合成、视觉遮罩局部修正、准确替换图片文字。

六条配方均为 Vistack 场景重新编写的纯文本模板，不带外部示例图。它们沿用现有模板插入流程，只写入主提示词；没有新增页面或常驻入口，也没有修改 API payload、供应商路由、模型参数、连接预设、参考图、历史或存储结构。

## 开发工具层的可选用法

这个 Skill 可以单独安装到开发者的 Codex 环境，用于：

- 快速验证某类提示词是否适合 GPT Image 2。
- 为 Vistack 的模板设计和回归样例生成测试素材。
- 对比相同提示词在 GPT Image 2 与现有供应商模型上的差异。

这属于开发工具，不等于产品融合，也不应读取或覆盖 Vistack 保存的 API Key。是否安装由使用者单独决定。

## 明确不做

- 不把 Python CLI 嵌进浏览器，也不新增仅为它服务的 Python 后端。
- 不用外部 Skill 的 API Key/.env 机制替换 Vistack 连接预设。
- 不复制整个 419 MB 仓库或 162 张示例图到生产包。
- 不用 GPT Image 2 的规则覆盖 Gemini、Grsai、Doraverse 等现有专用行为。
- 不因某个端点失败而静默切换协议或供应商重试。
- 不在 G1 中同时重构 `App.vue`、Storage v2、工具箱架构或历史数据库。

## 推荐决策

如果目标是 API 能力，推荐选择：**G1 能力档案先行，G2 原生遮罩随后。**

如果目标是提示词知识，推荐选择：**直接做 G3-lite，只提炼少量规则和配方，不改生成请求。**

G1 风险较小，并为模型参数和原生遮罩提供统一边界；G2 能改善局部编辑；G3 具有独立价值，但直接导入整库会带来包体和来源维护成本。三者不必被错误地绑成一个必须按顺序执行的整体。

## 当前执行状态

在尚未确认需要完整 GPT Image 2 参数或原生 mask 前，已先完成一个不调用 API 的六场景提示词价值验证包，并按用户后续明确选择实施了 G3-lite。

验证包只包含 6 个贴近 Vistack 主流程的改图场景：

- 保持人物身份进行环境或风格调整。
- 只换服装，保持脸、发型、姿态和背景。
- 只替换背景，保持人物和构图。
- 多参考图按角色合成。
- 局部细节修正并明确不变量。
- 海报或图片中的准确文字替换。

验证包保留原始需求、推荐提示结构、关键不变量、适用参考图角色、来源状态和预期观察点。G3-lite 只把对应的六条通用化配方写入内置模板数据，不复制上游示例图片，也不自动调用任何付费 API。

这个路径仍比直接改请求层更保守：当前运行时代码变化仅限内置模板数据和对应测试。真实 A/B 生成尚未执行，因此配方的实际质量收益仍需以后在用户确认素材和费用后验证；只有出现完整参数或原生 mask 的真实需求时，才启动 G1a。

状态更新：六场景验证包和 G3-lite 均已于 2026-08-15 完成，见 [`gpt-image2-prompt-validation-pack.md`](gpt-image2-prompt-validation-pack.md)。目前尚未执行真实生成，没有产生 API 费用；G1/G2 仍未授权实施。

后续任何 G1/G2、请求参数、界面入口或存储改动仍需单独确认。
